# 现场协作案例：把经历变成下一轮动作

以下是校赛小车、人脸跟拍云台、H 题滚球的历史问题抽象。它们说明排错方式，不是新项目的现成接线或最终参数。

## 1. “串口编码器 ticks 一直是零”

**信息错位**：用户看到串口数字，以为问题在串口；该工程实际由定时器采 A/B 相，串口只是显示。

**AI 做**：沿原始引脚状态 → 定时器计数 → 累计 ticks → 速度/距离追踪数据，必要时补最小诊断输出。

**人做**：在执行器失能且接线电平确认后，转动轮子，提供原始计数变化；是否有仪器决定进一步能排除到哪层。

**下一步依据**：信号没进入、定时器未计数、累计逻辑异常是不同问题。不要改打印格式或 PI 来掩盖原始计数问题。

## 2. “小车碰线还往前冲”

现场后来补充：线窄、通常只触发一两路、某路损坏。这些事实比通用的“多路同时触发才可靠”更能决定判据。

AI 先查进线条件、坏路屏蔽和捕线行为，人反馈碰线瞬间的真实触发状态。把“遇线”和“已居中稳定循迹”分开验证；先控制捕线过程，再优化速度。具体坏路索引随安装方向确认，别推广成“所有项目都屏蔽左三”。

## 3. “电机转得顺，但角度大得离谱”

依次核对：STEP/轴圈、编码器 count/轴圈、细分接线、齿轮齿条位移、真正的转轴到作用点力臂。管长和力臂可能不同；指令角度正确不证明物理角度正确。

AI 将换算链写清楚并查源码和器件资料，人提供接线与实际几何/低幅运动测量。先在保护条件下确认比例与方向，随后整定控制。禁止用加大故障阈值或调 PID 代替比例确认。

## 4. “视频、人脸检测、电机、网页都想要”

云台项目经历了增加视频、资源优化、回到跟随优先的取舍。AI 应把检测、控制、步进服务和通信的耗时分开测；人选择当前展示目标，反馈运动卡顿和实际跟随效果。

单阶段/两阶段、开/关视频的指标要绑定配置与场景。跟拍项目能主动放弃视频；H 题若要求图传录像，就应调整分工或链路，而不是删掉题目功能。也别把旧 README 的帧率当本轮新测结果。

## 5. “能运行了，为什么一合并又坏了”

连接前共同确认：数据格式、帧长、单位、正方向、采样时刻、新帧标志、超时和故障状态。历史文档里曾同时存在 8 字节毫米球位协议与 14 字节、0.1 mm 协议的说明。

AI 以当前收发源码与测试帧核对接口；人反馈设备实际版本和显示数据。视觉、执行器、底盘各自能跑之后，先接一条最短链；测试丢帧和断连，再开图传和整机流程。

## 6. “你说完成，但我的板子不是这个版本”

AI 必须分别说明：文件改完、编译通过、刷写校验通过、用户观察到动作、完整指标验证。提交标题叫“完美完成”也只是版本描述。

“上传”先区分推 GitHub 与烧录；“置零”区分软件登记与实体回零。发布只上传提炼后的案例，聊天中的账号、密码和原始附件不随复盘公开。
