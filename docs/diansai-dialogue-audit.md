# 从整段开发对话中提炼协作机制，而非事后罗列注意事项

2026-09-06 · 第二轮复盘 · 核心受众：大一新生、基础较弱的首次参赛者。

## 这次究竟看了什么

上一轮只抽取7个相关任务，得到的是“分工、反馈、最小验证”等原则。它们没有解释：为什么已经提醒过，类似误解仍不断回来；为什么每次都在做事，整体却可能后退。用户指出深度不足，这一轮改为从完整目录历史建立索引，再沿反复纠正追踪因果链。

### 覆盖和边界

- 本机历史数据库与活动/归档日志目录交叉核对，定位工作目录规范化后恰为电赛目录的 **30个历史主任务、44个子任务记录**；排除本次skill整理任务。磁盘额外扫描未发现该范围内索引遗漏的主任务。
- 主任务的message记录整理出995条用户、1577条助手文本条目；去除相同文本后为535段用户文本、1077段助手文本。它们含分叉继承、短回复和粘贴方案，**不是535次独立实验，更不是2572轮对话**。
- 完整阅读去重后的用户文本；助手部分先按全局时间线检索、浏览决策与交付摘要，再完整回读关键纠正段。另核对event记录，补读附件说明等差异。30个主任务均进入覆盖清单，未只挑成功案例。
- 44个子任务检查可读交付或末尾状态，用来区分实现、检索与复核；部分正文采用加密存储，可读event仅保留继承上下文，不将这些记录算作独立分析成果。
- 这是**全量发现和用户文本通读、助手决策链重点复读**，不是所有工具输出、图片、PDF和加密子任务正文的逐字复核。按项目规定跳过的受限工具/图示内容未作为技术证据，也未打开对应实物工程附件进行新验收。
- 相同长对话在分叉中大量重复：一组TMC主任务与分叉有436条相同消息序列。共性按不同问题链判断，不用复制次数制造统计显著性。
- 原始聊天、私人附件、路径、账号信息留在本地。公开的是脱敏概括与案例编号；本地证据台账保留9条链、142个引用条目的日志行号。这142个条目相互有重叠，不作为样本量。

**证据标签**：下文“人反馈”是当时现场自述；“AI分析/交付”是历史助手的判断或实现声称；“本次推论”是从往返过程提炼的机制。本次没有重跑固件或实物，不把历史诊断的语气当成因果证明。范围仅覆盖本机可定位记录，不代表其他聊天软件的全部历史。

## 总判断：难点是共同理解会漂移，而且漂移会累积

AI能局部解释代码，人能局部看到实物；两边都可能在各自的信息里自洽。真正昂贵的是两套理解没有及时对齐：代码中的“左”不是人眼里的左；“方法”被当成目标；“控制窗口”变成计分窗口；新源码被当成板上固件。

于是出现循环：**现场异常→双方给它一个解释→围绕解释修改→没有区分性证据→换一个解释再改**。这并非所有失败的原因，也不否认硬件接触、机械装配等真实问题。问题在于协作没有稳定地把这些可能性区分开。

AI的价值也不只是写代码。它承担过工程搭建、跨文件修改、模型计算、诊断界面、文档和发布；人承担过实物识别、尺寸测量、运行反馈、目标纠正与取舍。最有价值的交界处，是把人的低成本观察变成技术上能排除分歧的证据。

## C01｜有工具能力，仍可能没有共同操作现场

**过程（7月27—28日）**：HC05/VOFA任务中，AI先按SWD调试器检查烧录；人反复说明自己用的是板载USB数据线。之后转到串口下载，出现多次握手超时；网页操作也出现AI已载入固件、用户却看不到对应页面的错位。人明确要求空出串口自己处理，AI结束后台程序并报告释放；人随后反馈已烧好，再继续数据接收与曲线配置。

**本次推论**：协议和术语解释正确，还不足以完成协作。必须同时知道谁在操作哪一个窗口、哪条连接、哪个资源由谁持有。更长的说明解决不了“用户根本不在那个页面”。

**写入规则**：操作接力前释放本轮资源、交代状态与文件、让下一步可见；按真实拓扑区分下载通道与运行数据通道。不是规定全部由AI做，也不是规定烧录永远交给人。

## C02｜一开始就写完整控制器，反而推迟了第一次有效证据

**过程（7月29—30日）**：TMC早期工程包含UART、状态机、DIAG、限位和命令等依赖。人先后纠正模块没有DIAG、希望人工登记零点。串口无输出阶段又经历详细日志与重复烧录。后来人明确要求退到纯STEP/DIR/ENN空载测试；低速仍抖，最终人反馈端子松动得到处理，问题转入响应速度与位移测试。

**本次推论**：上层功能多，不代表诊断信息多。启动链中任一未验证条件都可遮住执行器本身；在失效观测通道上追加日志，信息收益可能为零。

**写入规则**：诊断模式隔离无关依赖，仍保留行程、电气与停机边界；一旦能动，回到正式路径测试。这个案例支持“减少无关门槛”，不支持“永久移除所有保护”。

## C03｜左右各自正确，完整反馈仍可能配错

**过程（7月29日—8月1日）**：巡线链先后调整电机取反、红外误差符号、PWM通道和编码器归属。出现过修正PWM映射后直线又失效，也出现过AI同步翻转电机和编码器之后，人反馈前进时速度与里程变负。更强的对照后来出现：Task1固定PWM能走直线，Task2闭环时两轮速度差距却扩大，约一侧1000、另一侧300。AI源码分析定位到输出API参数与编码器反馈左右交叉；后续交付将物理左右反馈与最终输出调用重新配对。

**本次推论**：单个“左/右/正负”判断不是系统不变量。一个错误可能被另一个错误暂时抵消；修掉一项会暴露另一项。修改“看起来反了”的符号，可能只是把错移到下一层。

**写入规则**：保存物理部件到反馈/输出的全链映射；用正常任务作对照，并用单侧扰动区分采集与输出关系。保留Task1已验证的行为，修Task2真正不同的路径。历史交付支持曾这样修正，不代表本次已重测最终闭环。

## C04｜真正该持久化的不是常量，而是常量的物理含义

**过程（7月31日—8月1日）**：编码器加入后白屏，AI先要求改变屏幕复位接线；人澄清现有接线基准，AI随后按实物恢复引脚用途。运动测试中，±100的边界曾被误当允许误差，生成±400测试目标；人再次指出行程限制。细分接线也曾被AI先解释为1/16、后来改正为1/32。方向修正后仍出现角度过大，人测量并确认真正力臂约67.8mm，而非250mm管长；后续又给出总行程与编码器端点值，更新实际传动比例。

**本次推论**：只保存“67.8”仍很脆弱。需要保存它是哪两个点之间的距离、哪次测量、哪些量依赖它。修正方向后残留的比例问题也说明，一个反馈可同时涉及多个错误层。

**写入规则**：纠正后明确依赖失效范围；单位、限位、测试轨迹、故障阈值成组核对。保护成功行为，而非死守已经被证据推翻的常量。历史计算里的精确小数仍不是独立测量。

## C05｜接口不是一段格式说明，而是两端已经共同到达的状态

**过程（8月1日）**：Task3在启动前报错；人提供K230的5字节格式，与接收端8字节预期不符，双方改约14字节协议。更新之后仍失败。AI逐步增加启动原因、帧状态，再增加字节/帧头/整帧/校验计数。屏幕显示接收字节为零时，排查才明确退回接收链，而不是继续改球位控制。人另说明K230校准约5秒、期间持续发送无效位置帧。

**本次推论**：说清协议、改好接收器、烧入接收器、发送端采用它、真实字节到达、球位有效，是不同事实。CRC正确只能说明某份帧自洽，不能证明它已到板上，更不等于可以启动。

**写入规则**：观测首个失败边界，版本按两端记录；通信存活与测量就绪分开。此链没有足够独立证据重建最终物理接收故障，不宣称已经证明是某根线。

## C06｜人反复纠正的，是概念边界，不只是数值

**过程（8月1日）**：软件校零曾同时开启持续保持，人反馈未启动就运动。AI后来拆开零点有效与执行器使能。Task5借Task3的保持方法时，AI把5cm目标也带过去，人纠正目标应是0。右端控制容差与比赛成功容差已经拆过一次，后来48—52mm的精细控制窗口又被用于5秒判定，人再次纠正成功范围应按40—60mm。另有DONE以后时间继续增长、执行器持续保持的反馈，促使计分、显示和结束后动作分开。

**本次推论**：把用户最新参数记住仍不足以避免复发。需要保留“这些东西不等价”的知识：方法≠目标、校零≠使能、控制窗口≠评分窗口、计分完成≠所有后台动作结束。

**写入规则**：已纠正的区别成为后续改动必须保持的关系；迁移前重申目的和边界，任务状态还需明确谁能继续写执行器。

## C07｜最小实验还必须对下一阶段有代表性

**过程（7月30日—8月1日）**：步进测试从整圈、往返速度、1.5°跳转逐步变化。人多次提醒最终用途是快速带动齿条稳定小球；独立能转的测试与实际Task3调用路径并不相同。后期改为ENC小幅切换，又区分了每秒目标切换次数与完整往复次数。用户要求复用“控制频率”时，AI检查到视觉周期相同，实际修改的是STEP上限与加速度。

**本次推论**：低风险测试有必要，却可能长时间回答错问题。整圈准确不证明带载快速换向；提升某个名义频率也不直接提升整机闭环效果。

**写入规则**：按待验证能力选择幅度、负载、频率和生产调用路径；得到证据后推进到下一层，别永远停在容易成功的演示。

## C08｜正常路径和失败版本，比“先进方案”更有诊断价值

**过程（7月29日—8月1日）**：独立图传采用双HTTP服务等稳定性重构并通过软件检查，用户反馈实际严重卡顿、旧版更稳定。AI从历史定位确切旧源码并回退。Task3后期则经历多个前馈、制动、保持方案；有过“完美完成”的提交描述，之后仍有偏差和振荡反馈。最后几轮曾把固定切换点、控制器、预测和D值同时改动，却把整组修改称为干净对照。

**本次推论**：架构理由与实测收益必须分开；“加了保护/更高频/更完整”不是效果证据。一次多因素调整能回答方案整体是否更好，却不足以锁定单个根因。定点保持成功也不证明能接管高速来球。

**写入规则**：保留版本与结果的对应，明确方案级试验的归因边界；迁移检查初始状态与控制器接管；需要回退时区分确切恢复和按描述重建。不把“最后一版”默认为“最好一版”。

## C09｜AI要解释真实工程选择，而非为每次改动补一套漂亮故事

**过程（8月1日）**：球位调试中，TRK曾被误当总输出，实际是目标与反馈的差；前馈、P、D及限速可能互相抵消。状态叫“制动”，历史代码分析却发现同向前馈仍存在。报告阶段，人要求着重讲设计思路，删去题目强制项的虚假选型竞争和无意义参数，并给出约25秒、约1cm等实际结果作为写作依据。

**本次推论**：显示标签、状态名、模型公式、报告措辞都可能让双方以为理解一致。AI应回到实际产生行为的链路，解释收益与代价；作文里的合理性不能倒过来证明工程达标。

**写入规则**：先识别数值到底代表什么；查实际合成输出和生效限制。写作区分真实选择、题目要求、作者实测、模型推算，不编造实验次数、完成率或精度。这里的历史成绩数据也不用于推断“新skill使项目获奖”。

## 为什么这对基础不高的人更重要

不是让新生多学一套管理流程，而是把AI的技术能力用在三个位置：

1. **翻译问题**：人说“只往一边转”“这个变红了”，AI把它翻译为能通过现场动作检验的分歧。
2. **保存纠正**：人已经测过、说清的事情，不应要求他一次次重新解释；AI负责追踪它影响哪些模块。
3. **承担决断**：AI能读的工程自己读，能完成的分析自己做；在需要现场事实时给具体动作，而非丢给人一屏假设。

新生需要逐渐掌握的不是所有代码细节，而是：目标是什么、手上正在操作什么、结果从哪里来、结果反驳了哪句话、下一步为何值得做。它让人能在做中学，也保留质疑AI的能力。

## 改版对应关系

| 初版不足 | 这次改变AI决策的要求 |
|---|---|
| “有新事实就更新”过于笼统 | 更新受影响依赖，保留概念区别及失效条件 |
| “最小测试”没有代表性边界 | 指明下阶段的输入状态、负载、幅度和真实调用链 |
| “一次改少一点”不足以保护系统 | 保护物理不变量，必要依赖成组修正，区分方案级与单因子归因 |
| “协议一致”停在静态说明 | 分开两端部署、字节到达、校验、有效测量和启动 |
| “复用成功代码”忽略工况 | 迁移机制，不复制目标；检查速度、前馈退出和输出所有权 |
| “人操作、AI写码”分工僵硬 | 动态操作接力，AI承担分析与观测设计 |
| 只提醒编译不等于实测 | 同时防止最新源码被误当板上版本、无反馈版本晋升稳定版 |

新版入口见 [SKILL.md](../skills/diansai-collab/SKILL.md)，具体分支见 [现场案例](../skills/diansai-collab/references/field-cases.md)，用真实反例审查设计见 [情境回放](collaboration-replay.md)。

**结论**：人与AI相处的核心，不是人永远相信AI，也不是AI永远顺从人；是双方对目标、实物、解释和版本的理解能被现场证据持续修正，并且修正真正留在下一次行动里。
